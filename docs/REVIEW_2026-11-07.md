## 2. 🔴 必须修（数据/功能级）

### B1. 批量添加词条：PG 上「一条重复 → 整批失败 + 500」

`app/routes/api.py:1541-1547`

```python
with database.write_txn() as conn:
    for t in ordered:
        try:
            conn.execute(star_terms.insert().values(term=t, note=note, enabled=1))
            added += 1
        except Exception:
            skipped += 1   # 唯一键冲突 = 已存在
```

**为什么是 Bug**：PostgreSQL 里任何语句报错都会把**整个事务**置为 aborted（`25P02`），后续语句全部失败，`engine.begin()` 退出时 COMMIT 也会失败并抛异常。  
于是「用户粘一批名单，里面夹着几个已存在的名字」→ 逐条 `except` 吞掉错误（`added` 还在涨，是假象）→ 提交时抛 `PendingRollbackError` → **500，整批一个字都没进去**。

SQLite 不会中止事务，所以 `test_v190_related.py` 全绿——**这是测试后端造成的盲区**。

**修法**（顺带把「逐条往返」变成一次批量）：

```python
stmt = database.dialect_insert(star_terms).values(
    term=bindparam("term"), note=note, enabled=1
).on_conflict_do_nothing(index_elements=["term"])
with database.write_txn() as conn:
    res = conn.execute(stmt, [{"term": t} for t in ordered])
added = res.rowcount or 0
skipped = len(ordered) - added
```

**同类隐患**（一并排查）：`star_terms_update` 里 `res.rowcount` 为 0 时抛 404——这在 PG 没问题（没有约束错误），但**不要**在事务里用「先 insert 再靠异常判重」的写法，本仓库已有一处（`_flush_map_insert` 用了 `on_conflict_do_nothing`，是对的）。

### B2. `reset_algo_version()` 的 DELETE 从不提交 → 算法升级不生效

`app/related.py:812-821`

```python
with database.engine.connect() as conn:
    n = conn.execute(
        vod_related.delete().where(vod_related.algo_version != config.RELATED_ALGO_VERSION)
    ).rowcount or 0
```

SQLAlchemy 2.0 的 `Connection` 是「commit as you go」：**不 commit 就 rollback**。这里既没 `conn.commit()` 也没走 `write_txn()`，DELETE 在连接归还时被回滚，但 `rowcount` 照样返回 1 —— 日志还会打印「清空 1 条旧推荐结果」，看着像成功了。

**实测证据**：

```
[1] reset_algo_version 报告删除 1 行；事后实际剩余行数=2（期望 1 = 只剩新版本行）
```

**影响**：改了 `RELATED_ALGO_VERSION` / 权重 / 阈值后，旧结果永远留着；`vod_related` 的主键是 `(slug, vod_id)`，新一次重算会 UPSERT 覆盖，所以**已经重算过的站**没事，但只要重算没跑完（或 `RELATED_ENABLED` 关过一阵），库里就是新旧算法混杂，且没有任何地方按 `algo_version` 过滤读路径。

**修法**：

```python
with database.write_txn() as conn:
    n = conn.execute(...).rowcount or 0
```

另外建议在 `get_related_entries` 加一句 `algo_version == 当前` 的过滤（读路径自证版本），避免任何「旧结果被当新结果」的可能。

**顺带排查同类**：全仓 `engine.connect()` 里做写操作的地方只有这一处（`auth.get` 是读、`housekeeping` 用了 `write_txn`、`syncer` 的写都走 `write_txn`）。这条纪律建议写进 CONTRIBUTING：**读用 connect，写必须 write_txn**。

### B3. 词库删改后旧 `vod_tag` 永久残留

`app/star_tags.py:144-147`（只有 `hits` 非空才回写）

```python
if src == "title":
    new_tag = ",".join(hits)
    if (r["vod_tag"] or "") != new_tag:
        batch_tag.append({"vid": r["vod_id"], "tag": new_tag})
```

**实测**：

```
[A] 词条=吴京  rebuild 后 vod_tag = '吴京'
[B] 词库换成沈腾 rebuild 后 vod_tag = '吴京'  star_map 行数 = 0
```

`star_map` 清了、`vod_tag` 没清；而 `upsert_batch` 对 `vod_tag` 用的是 `COALESCE(NULLIF(excluded,''), 本地值)`（v1.9.1 的保护），所以**连源站重同步也洗不掉它**。

**影响路径**：`star_tags.star_related` 的兜底分支会读 `vod_tag` 当目标明星（`star_tags.py:326-329`），于是删掉的明星仍然被当成「该视频的明星」→ 走 `star_map` 查不到 → 返回空列表；面板上 tag 与映射也对不上。

**修法**：全量重建时先把该源站**由推断写入的** tag 清空（不能一概清，真实源的 tag 要保留）。  
最省事的做法：`_scan_and_collect` 在 `src == "title" and not hits` 时也写 `""`（判空跳过发 SQL 的优化可以保留，但要**记录**并统一清理），或重建前执行  
`UPDATE vod_{slug} SET vod_tag='' WHERE vod_tag <> '' AND vod_actor = ''`（缺演员行才可能是推断值）。

### B4. GBK / 非 UTF-8 源站：片名被静默替换成 U+FFFD

`app/maccms.py:276`

```python
data = json.loads(resp.content.decode("utf-8", errors="replace").lstrip("﻿"))
```

`errors="replace"` 会把 GBK 中文字节替换成 `�`，**JSON 结构（ASCII）仍然合法**，所以 `json.loads` 成功、不报错 —— 结果是整站片名/演员变成 `����`，而且会一路 UPSERT 进库，覆盖掉之前正常的数据。  
（代码注释自己写了「部分源站返回 GBK」，实现却没处理。）

**修法**（3 行）：

```python
raw = resp.content
try:
    text = raw.decode("utf-8")
except UnicodeDecodeError:
    enc = (resp.encoding if resp.encoding and resp.encoding.lower() not in ("utf-8", "ascii")
           else ("gb18030" if _looks_gbk(raw) else "utf-8"))
    text = raw.decode(enc, errors="replace")   # gb18030 是 GBK 的超集
```

更稳的做法：从 `Content-Type` 取 charset，其次看 JSON 是否带 BOM，最后 `gb18030` 兜底；并**加一条断言**：解析出的 `vod_name` 若含 `\ufffd` 就整页丢弃 + 记 warning（宁可漏一页，不要污染整站）。

## 5. 💭 算法合理性（重点）

### A1. 「权重重分配」在数学上没有下界 → 稀疏数据得分通胀（🔴 影响质量）

现在的打分是：
```
score = Σ(w_i · sim_i) / Σ(w_i)      # 只对「双方都有值」的字段求和
```

这在**字段齐全**时是对的；但数据现实是「标题 + 分类」最常见。于是出现：

| 场景 | 计算 | 得分 |
|---|---|---|
| 同分类 + 同年代，标题毫不相干 | (0.30·1 + 0.10·1 + 0.20·0) / 0.60 | **0.667** |
| 标题「流浪地球」vs「流浪地球2」，分类不同 | 标题 0.36 + 年份相邻 0.05 + 分类 0 | **0.383** |

**同一部片的续作，排在「同分类的随机片」后面。** 这是排序反转，不是阈值问题——阈值调到 0.7 也只是把两者一起砍掉。

**根因**：分母只统计「可用字段」，字段越少，单个弱信号越接近 1.0；`class`（52 站共用十几个大类）权重 0.30，是最大的权重，却几乎不含区分信息。

**建议（按代价排序）**：
1. **加证据先验（最小改动）**：
   ```python
   LAMBDA = 0.6            # 相当于「0.6 分权重的虚拟字段，全部给中性分 0.4」
   score = (Σw·sim + LAMBDA*0.4) / (Σw + LAMBDA)
   ```
   于是 1 个字段满分 → (0.3+0.24)/0.9 = 0.60；3 个字段全对 → 0.85。**稀疏数据不再自动封顶**，且不需要改数据结构。
2. **降 class 权重、升 title 权重**：`class:0.30 → 0.15`、`title:0.20 → 0.35`（标题是唯一全量信号）。地区/年代同理可降到 0.05。
3. **最小证据门控**：`total_w < 0.35` 时直接把 `m="fb"` 走兜底，别当作「相似」放进推荐位——用户对「推荐位里是同分类随机片」的观感比「没有推荐」更差。

### A2. 演员相似度用 `min(len)` 作分母 → 客串被当主演

`_set_sim = inter / min(len(a), len(b))`：目标 10 位演员、候选 1 位（且是客串）→ **1.0**。
建议：`inter / len(target)`（以目标为基准）或取前 2~3 位主演比；再乘 `1/log(1+len)` 抑制长名单。

### A3. 演员名没归一化 → related 与 star_tags 两套口径

`_feat` 里 `actor_set = _split_set(vod_actor)` 是**原样切分**；而 `star_tags._actor_hits` 走了 `_star_norm`（NFKC + 繁转简 + 别名归一）。
后果：繁体站（`吳京`）与简体站（`吴京`）在「相关推荐」里永远不共享演员；而「明星作品」里是共享的。**同一个概念两套实现，必然漂移**。
建议：`_feat` 里对 `actor/director/writer` 先过 `_star_norm`（成本：1 万行 +0.1s），别名归一可选（别名依赖词库，运行时可能变）。

### A4. 兜底链会「污染」推荐位观感

零命中时一次性补 12 条同分类最新，条目 `score=0, m=fb`，但排序里和真命中混排；客户端只有 `related_fallback` 一个总开关，分不清哪条是兜底。
建议：兜底最多填 **4~6 条**，并在卡片上带 `mode` 让客户端能分区展示（「猜你想看」）。

### A5. 「标题命中 + 字段稀疏 = 强信号」的边界

规则本身是对的（用户明确要求），但缺少**否定条件**：`吴京的访谈`、`盘点吴京十大名场面`、`吴京同款` 这类标题也会进 strong。
建议加两条廉价规则：① 标题含「访谈/花絮/解说/盘点/合集/预告」等词 → 降为 `inf`；② `type_name` 属于综艺/纪录片时 `strong` 系数 ×0.8。

### A6. `title_similarity` 的归一化分母

`0.6·LCS/min(len) + 0.4·Jaccard`：`战狼` vs `战狼2` → LCS 2 / 2 = 1.0（序号不同会 ×0.5 兜住）。但 `英雄` vs `英雄本色` → 1.0×0.6 + Jaccard(0.5)×0.4 = 0.8，**短标题包含长标题一律高分**。
建议改用 `LCS / max(len)`，或对 `len` 差 > 2 的再乘 0.85。

### A7. 排序稳定性

`_rank` 只按 score 排，同分时依赖候选插入顺序（见 C4）。推荐位每次刷新顺序不同，用户会觉得「乱跳」。
建议 `scored.sort(key=lambda x: (-x[1], -int(x[0]["time"][:4] or 0), x[0]["id"]))`，稳定可复现。

## 6. 测试策略的盲区（这才是最该补的一块）

- 15 个测试脚本全跑 **SQLite**。SQLite 与 PG 的差异恰好落在本项目最吃紧的地方：
  - **事务错误语义**（B1）：SQLite 语句级回滚，PG 事务级中止 —— 所以 B1 测不出来；
  - **并发写**：SQLite 靠进程内锁串行，PG 真并发 —— `star_map` 重建期读残缺（C10）只在 PG 上明显；
  - **`count(*)` 成本**：SQLite 快，PG 全表扫 —— P7/P9 测不出来；
  - **`FOR UPDATE` / 隔离级别**：本仓库没用，OK。
- 建议：`docker-compose.yml` 里已经有 PG，加一个 `scripts/test_pg_smoke.py`（用 `DATABASE_URL` 指向 PG 容器，跑 6 个关键用例：批量重复词条、algo_version 清理、并发 rebuild、`/videos` 无 source、推荐 Top12 非空、增量水位线）。CI 里跑一次即可，成本 1~2 分钟。

## 7. 做对了的地方（重构时别改坏）

1. **全量断点落在「连续完成前缀」+ 失败页重试**（`full_sync` 的 `written_upto`）—— 这是 v1.5.2 三个 P0 里最难修的一个，修法是对的。
2. **水位线只按「真的写进库」的时间推进 + 失败 ID 封顶**（`incremental_sync` 第 4 步）—— 数学上闭环。
3. **`star_tags` 的 keyset 分页 + 单正则 + 演员集合交集**：复杂度与词库规模解耦、内存恒定，是这一版最漂亮的设计。
4. **`multiquery` 的 top-K 归并**：注释里给了精确性证明（全局第 N 行必在某表前 N 行内），并且保留了 UNION 回退，宁可慢不少给数据。
5. **`/healthz` 恒 200 + `degraded`**：避免「DB 忙 → 健康检查失败 → 重启 → 更忙」的死亡螺旋。
6. **UPSERT 对 `vod_tag` 的 `COALESCE(NULLIF(...))` 保护**：思路对（虽然引出了 B3 的清理缺口）。
7. **代理降级用独立异常 `_RouteFailed`**：403 立即切路由而不是白等 3 次重试。
