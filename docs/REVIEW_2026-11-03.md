## 0. 结论先讲

**整体工程质量在个人项目里属于中上**：幂等写入、断点持久化、并发闸门这三件事想清楚了，不是"能跑就行"的水平。
但**同步链路上有 3 个数据完整性缺陷，其中 2 个会让数据永久缺失且界面显示"成功"** —— 这类问题比崩溃更危险，因为它不报警。

| 维度 | 评分 | 说明 |
|---|---|---|
| 架构清晰度 | ★★★★☆ | 分表 + Core + 线程池，职责分明；`META` 复用是小隐患 |
| 中断恢复能力 | ★★★☆☆ | 全量有断点、增量靠幂等重跑；**但重启不自动续跑，日志永远 running** |
| 数据一致性 | ★★☆☆☆ | **3 个已复现缺陷**：丢页、水位线越界、增量单页失败整站失败 |
| 并发与过载保护 | ★★★★☆ | v1.4.1 的闸门+写串行是对的；`/videos` 无 source 查询仍是性能炸弹 |
| 可观测性 | ★★★☆☆ | 有 sync_logs 但无清理、无 interrupted 态、fetched 口径混乱 |
| 安全 | ★★★☆☆ | 鉴权设计扎实；**X-Forwarded-For 可伪造绕过登录锁定** |
| 部署健壮性 | ★★★★☆ | 健康检查恒 200 避免重启风暴；WAL 从不 checkpoint 是遗漏 |

**如果只做三件事**：修 P0-2（全量丢页）→ 修 P0-3（水位线越界）→ 修 P0-1（增量异常处理）。
其余都是"锦上添花"，但这三件是"数据在悄悄变少"。

## 1. 同步链路回顾（先对齐事实）

```
全量 full_sync：
  page1 取 pagecount → 按 PAGE_CONCURRENCY 并发抓一批页 → 逐页 UPSERT（每页一个事务）
  → 每 CHECKPOINT_EVERY_PAGES 页存 last_page → 全部完成 → _finish_full 清断点 + 水位线=库内 max(vod_time)

增量 incremental_sync：
  ① ac=list 翻完所有页 → 内存 index{vod_id: vod_time}
  ② 候选 = vod_time > watermark（可选 + 本库缺失的 ID）
  ③ 候选按 50 个一批 ac=detail&ids= → UPSERT
  ④ 水位线 = index 里最大的 vod_time
```

这个设计本身是对的（轻量索引 + 按需详情，百万级存量零重复传输）。问题都出在**错误路径**上——正常路径跑得很漂亮，异常路径没人走过。

## 2. P0：三个已复现的数据缺陷

### P0-1 增量同步「某一页失败」→ 整个源站的增量任务直接崩

**位置**：`app/syncer.py:511-518`

```python
with ThreadPoolExecutor(max_workers=len(batch)) as pool:
    for fut in as_completed({pool.submit(collect, p): p for p in batch}):
        try:
            index.update(fut.result())
            stats["pages"] += 1
        except MacCmsError as e:
            log.error("[%s] 增量 list 第 %s 页失败: %s", slug, fut.result() and "", e)  # ← 这里
```

`except` 分支里又调了一次 `fut.result()` —— 对已抛异常的 Future 调用 `result()` 会**重新抛出该异常**。
结果是：本该"跳过这一页继续"的容错逻辑，变成"把异常再抛一次"，一路冒泡到 `sync_source` 的兜底 `except`，整站增量判失败，**连第 1 页已经拿到的候选也不会写入**。

实测（附录 A）：3 页数据、第 2 页失败 → `!!! 未被吞掉的异常: MacCmsError 模拟第 2 页抓取失败`。

**影响**：源站只要有一页 5xx（大站几千页，概率不低），该站增量就完全失效；表现为面板上该站"同步失败"，而日志里的原因指向一个根本不存在的错误。

**修法**（3 行）：

```python
page_no = futures[fut]
try:
    index.update(fut.result())
    stats["pages"] += 1
except MacCmsError as e:
    failed_pages.append(page_no)
    log.error("[%s] 增量 list 第 %s 页失败: %s", slug, page_no, e)
```
索引阶段漏页会导致"候选集不全"，但因为是"漏判新片"而非"误判"，下次增量会补上（水位线未推进时才成立——见 P0-3，两者要一起修）。

### P0-2 全量同步「批内单页失败」→ 静默丢数据，且标记为已完成

**位置**：`app/syncer.py:353-383`（抓取循环）+ `449-467`（收尾）

```python
results = []                       # 只收集成功的页
...
except MacCmsError as e:
    consecutive_fail += 1          # 失败的页只计数，不进 results，也不记录是哪一页
...
last_done = max(r["page"] for r in results)
_save_checkpoint(slug, last_done)  # 断点 = 成功页的最大页码
pg = last_done + 1                 # 直接越过中间失败的页
```

批大小 4 时，若第 3 页失败、1/2/4 成功 → `last_done = 4` → 断点存 4 → 循环结束 → `_finish_full()` **无条件清断点、把水位线推到库内 max(vod_time)**。

实测（附录 B）：4 页 40 条、第 3 页恒定失败 → **入库 30 条，`last_page=0`，`watermark` 已推进，`stats` 里没有 error 字段**。

三重恶果：
1. 那 10 条**永远缺失**（断点已清，全量不会再跑）；
2. 水位线已越过它们的 `vod_time`，**增量也永远不会补**；
3. 面板显示 100% 完成，日志显示 `fetched: 30` 看着正常 —— **完全静默**。

**修法（推荐 A）**：记录失败页，收尾前重试一轮；仍有失败则**不进入 `_finish_full`**，把断点回退到 `min(失败页) - 1` 并写 `stats["error"]`，下次调度自动从那里重跑（UPSERT 幂等，重复抓几页的代价远小于永久丢数据）。

```python
failed_pages = set()
...
if failed_pages:
    _save_checkpoint(slug, min(failed_pages) - 1)
    stats["error"] = f"{len(failed_pages)} 页抓取失败，断点回退至第 {min(failed_pages)-1} 页"
    return stats          # 不调用 _finish_full，水位线不动
```

**修法（B，更省事）**：批内只要有失败页，立刻 `_save_checkpoint(slug, min(failed)-1)` 并 `return`，让外层按失败处理。
代价是"一页失败就中断整轮全量"，但至少不丢数据，且下次自动续。

> 顺带说明：`consecutive_fail` 这个变量的语义是"连续失败"，但因为 `if results: ... elif consecutive_fail >= N` 的结构，它实际只在"整批全失败"时才生效。名称与行为不符，改的时候建议改名 `batch_all_failed`，否则以后看代码的人会误判。

### P0-3 增量水位线「越过未入库的记录」→ 这些记录永远不会被补

**位置**：`app/syncer.py:554-575`

```python
for i in range(0, len(ids), 50):
    try:
        payload = client.fetch_detail_by_ids(src_api, chunk)
    except MacCmsError:
        continue                                   # ← 这一批 50 条全部跳过，无记录
    ...
max_time = watermark
for vid, (t, _tid, _n) in index.items():           # ← 用"索引里的全部时间"取 max
    if t > max_time:
        max_time = t
_mark_synced(slug, max_time, len(index))
```

水位线取的是 **index 里所有条目的最大 `vod_time`**，与"这一条到底有没有写进库"完全解耦。
只要某条候选的详情没拿到（该批失败、源站返回不全、字段被过滤），它的时间戳照样会把水位线抬过去。

实测（附录 C）：2 条候选，详情只返回 1 条 → **入库 1 条，水位线 = `2026-03-02 00:00:00`（就是没入库那条的时间）**。
此后增量筛选条件是 `t > watermark`，那条记录 `t == watermark` → **永久跳过**。除非打开 `INCR_CHECK_MISSING=true`（默认关闭，因为它要全表扫一遍）才有机会补回来。

**修法**：

```python
written_max = watermark          # 只统计"真正 upsert 成功"的行的 vod_time
missing_times = []               # 没写进去的候选，记下它们的时间戳
...
for it in payload.get("list") or []:
    row = MacCmsClient.extract_row(it, class_map)
    if row and row["vod_id"] in want:
        rows.append(row)
        written_max = max(written_max, row["vod_time"])
want -= {r["vod_id"] for r in rows}
...
_candidates_min = min(missing_times) if missing_times else None
new_wm = written_max if not _candidates_min else min(written_max, _candidates_min)
```

即：**水位线只能推进到"已确认入库的数据"的时间点**，未入库的按下界兜住。
另外建议把"源站返回的条数 < 请求条数"也计入缺失（现在只按 `row["vod_id"] in chunk` 过滤，少返回就当没发生）。

## 3. P1：影响可用性/安全，建议下一轮修

### P1-1 断电重启后不会自动续跑，日志永远卡在 running

现状（`main.py:_bootstrap`）：启动只做 `refresh_counts()` + `start_scheduler()`，**不扫描 `last_page > 0` 的源站**。

于是断电后的表现是：
- 全量断点还在（`last_page` 持久化，✅）；
- 但任务不会自己继续，要么等下一个 **6 小时**调度（`sync_all("auto")` 遇到 `last_page>0` 会走 full 从断点续），要么你自己去面板点「继续」；
- `sync_logs` 里那条 `status='running'` 的记录**永远是 running**（没有进程会来收尾），面板"最近日志"里挂着一条永不结束的任务。

**修法**：

```python
# on_startup 里，_bootstrap 增加
_wake_interrupted_logs()                      # UPDATE sync_logs SET status='interrupted', finished_at=now WHERE status='running'
if config.AUTO_RESUME_ON_BOOT:
    threading.Timer(60, _resume_pending).start()   # 延迟 60s，等源站列表/DB 就绪
```
`_resume_pending()` = 查 `last_page>0 AND enabled=1 AND paused=0 AND auto_sync=1` → 逐个 `sync_source(slug, "full")`（受并发闸门约束，天然排队）。
新增 `AUTO_RESUME_ON_BOOT`（默认 true），给"不想一开机就占满带宽"的人一个开关。

### P1-2 登录锁定可被 `X-Forwarded-For` 伪造绕过

`api.py:33-35` 无条件信任请求头：

```python
def _client_ip(request: Request) -> str:
    fwd = request.headers.get("x-forwarded-for", "")
    return (fwd.split(",")[0].strip() if fwd else request.client.host)
```

攻击者每次请求换一个伪造的 XFF，`LOGIN_MAX_FAILS` 永远达不到 → 六位默认密码**可以无限次尝试**。
（反过来，若挂在反代后面且不读 XFF，则所有人共用反代 IP，一个人输错 5 次锁住所有人。）

**修法**：加 `TRUST_PROXY`（默认 false）。false 时只用 `request.client.host`；true 时取 XFF 的**最后一段**（最接近服务的、由可信代理追加的那一段），而不是第一段。

### P1-3 `/api/v1/videos` 不带 `source` 是全表 UNION

`api.py:916-963`：`source` 为空 → 对**全部 52 张表**做 `UNION ALL`，然后 `count(*)` + `ORDER BY vod_time DESC`。
220 万行的库上，这个查询每次都要合并 + 全排序，无索引可用，单次可能是秒级到十秒级；而 App 的"首页推荐"很可能就是这么调的。

**修法（按性价比排序）**：
1. 文档写明"App 请务必带 `source`"，并把不带 source 的 `total` 改成 `sum(sources.total_videos)`（近似值，省掉 count）；
2. 或者对"无 source"的请求加 2 秒级超时 + 503（让客户端退避），而不是拖住连接池；
3. 真要做全站聚合，得另建一张 `vod_all` 汇总表（或物化视图），不适合现在做。

### P1-4 `pause_state.json` 非原子写，断电可能丢掉"暂停"意图

`pause.py:55-62` 直接 `open(path, "w")` 覆盖写，没有 `fsync`、没有 rename。
断电恰好落在写入瞬间 → 文件变成空/半截 → `load_state()` 解析失败 → **按"未暂停"处理** → 你本来暂停了全量，重启后它自己开始跑。

**修法**：写 `pause_state.json.tmp` → `flush + os.fsync` → `os.replace()`。3 行改动，标准做法。

## 5. 断电/重启恢复能力矩阵（你问的第二个问题）

| 场景 | 现在会怎样 | 结论 | 该补什么 |
|---|---|---|---|
| **全量同步中断电** | `last_page` 停在最近检查点（每 5 页），已提交的页都在；重启后数据一致 | ✅ 不丢已入库数据<br>❌ 不自愈 | P1-1：启动后自动续跑（现在要等 6h 或手点「继续」） |
| **增量同步中断电** | 水位线在最后才推进 → 重启后重跑整个候选集，UPSERT 幂等无重复 | ✅ 正确 | 大批量时可加断点（P2-10） |
| **写事务进行中断电** | SQLite 回滚未提交事务；WAL 帧有序，只会丢"尾部已提交但未落盘"的少部分（`synchronous=NORMAL`） | ✅ 不会损坏 | 若要零丢失改 `synchronous=FULL`（写入变慢，不建议 NAS 上用） |
| **重启后日志状态** | `sync_logs` 的 `running` 永远留着 | ❌ 面板显示一个永远在跑的任务 | P1-1 里的 `interrupted` 收尾 |
| **暂停状态** | JSON 非原子写，可能丢 | ⚠️ 小概率反转用户意图 | P1-4 |
| **PG 中断电** | PG 自身 crash recovery（默认 fsync 全开） | ✅ | 无需改动 |
| **容器被 OOM/Kill** | 同"断电"路径；`restart: unless-stopped` 会拉起 | ✅ | 加 `stop_grace_period` 更优雅 |

**一句话答**：**数据本身是安全的**（幂等 + 每页一事务 + 断点在库），**但"自动接着干"这件事没做**——现在只能手动点「继续」，或等下一次定时调度。这是我建议优先补的一块体验。

---

## 6. 做对了的地方（别在重构时改坏）

1. **每页一个事务 + `ON CONFLICT DO UPDATE`** —— 任意点中断都能重跑，这是整套恢复能力的地基。
2. **断点存 DB 不存内存** —— 容器重启不丢进度（相比很多项目存 Redis/内存，直接赢）。
3. **暂停是"检查点式"而非杀线程** —— 不会留下半批数据，这个取舍是对的。
4. **v1.4.1 的并发闸门 + 写事务串行化** —— 你那次 NAS 崩溃的根因（连接池被等锁线程占满）修得很到位。
5. **代理降级用独立异常 `_RouteFailed`** —— 403 立即切路由而不是白等 3 次重试，这个细节很多项目想不到。
6. **`/healthz` 恒 200** —— 避免"DB 忙 → 健康检查失败 → 容器反复重启 → 更忙"的死亡螺旋，这是踩过坑才会写的。
7. **52 张分表** —— 按 source 查询的场景下，比单张大表索引效率高、清理单站数据也简单。别为了"跨站排序"合并成单表（那是另一种代价）。

## 7. 建议的推进顺序

| 批次 | 内容 | 改动面 | 风险 | 验证方式 |
|---|---|---|---|---|
| **Wave 1（今天）** | P0-1 / P0-2 / P0-3 + P1-4 + sync_logs interrupted + P3-1 | `syncer.py` 约 80 行、`pause.py` 5 行、`main.py` 15 行 | 低（都是错误路径） | 新增 `test_v160_integrity.py`：单页失败不崩、丢页不静默、水位线不越界、pause 原子写 |
| **Wave 2（本周）** | P1-1 自动续跑、P1-3 XFF、WAL checkpoint、日志清理 | 中等 | 中（启动行为变化） | 重启压测：kill -9 容器 → 观察 60s 后自动续跑、日志变 interrupted |
| **Wave 3（视需要）** | P1-2 无 source 查询、P2-8 count 优化 | 大 | 中 | 220 万行库上压测 P95 |

**不建议做的**：
- 引入 Celery/Redis 做任务队列 —— 单机 52 站、每天几千次请求，线程池足够，加中间件只会多一个要维护的东西。
- 多副本/多 worker 部署 —— 内存态（暂停、闸门、代理记忆）决定了它现在是"单实例"架构，要支持多实例得先把状态搬到 DB/Redis，收益不成正比。
- 把 52 张表合并成 1 张 —— 查询模式是按 source 过滤，分表更优。
