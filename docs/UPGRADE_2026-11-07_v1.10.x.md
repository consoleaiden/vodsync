> 发布：`v1.10.0`（算法/性能，2026-11-07）、`v1.10.1`（详情字段，2026-11-07） ｜ 基线：`v1.9.3`（`56886f3`）

## 2. 接口详解

### 2.1 `GET /api/v1/related` — 相关推荐

请求参数**完全不变**（`slug` / `id` / `limit`）。

```json
{
  "code": 1, "slug": "jkun", "vod_id": 134369, "limit": 12,
  "fallback": false,
  "computed_at": "2026-11-07T04:30:12",
  "algo_version": "2",
  "list": [
    { "vod_id": 135001, "vod_name": "流浪地球2", "vod_pic": "https://...",
      "vod_remarks": "HD国语", "type_name": "科幻片",
      "source": "jkun", "source_name": "优质资源",
      "score": 0.691, "mode": "match", "reason": "title,class" }
  ]
}
```

新增字段：

| 字段 | 位置 | 说明 |
|---|---|---|
| `algo_version` | 顶层 | 当前算法版本，本版为 `"2"`。算法升级后旧值会被自动清空重算，缓存 key 带上它即可自动失效 |
| `reason` | 卡片级 | 命中原因，逗号分隔。取值 `title` / `actor` / `director` / `writer` / `class` / `area` / `year`，按贡献排序取前两位。兜底条目为空串 |

**行为变化（这是本次唯一需要产品/前端一起确认的点）：**

1. **"仅同分类"不再算相似。** 旧版对「同分类 + 同地区 + 同年代、但标题毫不相干」的两部片给 **0.714**（阈值 0.15），比「同导演同演员」的 0.368 还高 —— 推荐位实际退化成了"同分类最新"。本版这类配对直接判 0（`reason` 为空），改走兜底链。
   → **表现**：某些冷门/字段稀疏的影片，推荐条数会比以前少，这是**修正**而不是故障。
2. **兜底最多 6 条**（`RELATED_FALLBACK_LIMIT`，原为 12），且**不再与真命中混排**。`fallback=true` 表示整条列表都是兜底；此时 `score` 恒为 0、`mode` 为 `"fallback"`、`reason` 为空串。
3. **列表仍然永远非空**（只要视频本身存在）：预计算结果缺失时服务端会实时兜底。

**给前端的建议写法：**

```js
// 推荐栏
if (resp.fallback) {
  renderSection("猜你想看", resp.list);      // 整条都是兜底，别当"相似推荐"
} else {
  renderSection("相关推荐", resp.list);      // 可能只有 1~3 条，属正常
}
// 可选：副标题
const subtitle = c.reason ? `因为同样${reasonLabel(c.reason)}` : "";
```

### 2.2 `GET /api/v1/videos` — 列表 / 批量详情

```json
{ "code": 1, "page": 1, "pagecount": 133, "total": 2640,
  "total_approximate": true,
  "list": [ ... ] }
```

- **出现条件**：不带 `wd` / `type_id` / `type_name` / `ids`（即"全站列表"）时。带筛选条件时 `total` 仍是精确值，也不会出现该字段。
- **来源**：`SUM(sources.total_videos)`（后台同步一直维护的数字），替代 52 张表各跑一次 `count(*)`。代价是 `total` 与 `pagecount` 可能差 1~2 页（只在翻到最末页时才能感知）。
- **建议**：
  - 展示「共 ~2640 条」时判断 `total_approximate`，把文案降级为「约 N 条」；
  - **无限滚动/翻页的终止条件请用「本页返回条数 < page_size」**，不要用 `page >= pagecount`（估值可能多算一页，导致最后一页空列表）；
  - `ids` 批量详情分支不受影响。
- 精确值每晚由校准任务重算一次（凌晨），`TOTAL_APPROXIMATE_ENABLED=false` 可关掉该优化。

### 2.3 `GET /api/v1/star/related` — 明星维度推荐

`truncated` 的语义修正：

- 旧版用 `count(distinct vod_id)` 判"是否还有更多"，结果**几乎恒为 `true`**（哪怕总命中只有 3 条）→ 客户端「查看更多」按钮常亮却点不出新内容。
- 本版多取 1 条判断，**命中不足 `limit` 时 `false`**。字段名与结构不变。

### 2.4 `GET /api/v1/categories` / `GET /api/v1/star-terms`

- `categories` 多一个 `cached`（`true` = 命中服务端缓存，默认 300 秒）。纯诊断字段。
- `star-terms` 的 `active` 改为**返回进程内当前生效的启用条数**（不再每次请求重编译词库正则）。写操作（增/删/改）会立即 reload，所以面板看到的是新值；多副本部署时其他实例最迟在重启或下一轮定时任务后一致。

## 3. 算法升级：分数为什么变了

### 3.1 根因

旧公式 `score = Σ(w·sim) / Σ(w)` **只对"双方都有值"的字段求和**。字段越稀疏，分母越小，单个弱信号被放大到接近 1.0 —— 这是"稀疏数据得分通胀"。实测三处失真：

| 失真 | 旧行为 | 后果 |
|---|---|---|
| 稀疏数据通胀 | 「同分类+同地区+同年代、标题毫不相干」= **0.714** | 推荐位 = 同分类最新列表 |
| 排序反转 | 「同演员+同导演、片名不同」= **0.368** | 真·相关片排在假·相关片后面 |
| 短标题包含 | 「青云志」vs「青云路」= **0.286** | 两字短标题被整体包含就拿高分 |

### 3.2 改法

1. **证据先验**：`prior = λ × (缺失权重 / 总权重)`，`score = (Σw·sim + prior × NEUTRAL) / (Σw + prior)`（`λ=0.6`，`NEUTRAL=0.4`）。缺失字段不再"不计入"，而是注入一份中性分 —— 稀疏数据不再自动封顶。
2. **权重回归语义**：标题 0.20 → **0.35**（唯一全量信号），分类 0.30 → **0.15**（52 站共用十几个大类，几乎不含区分度），地区/年代降为语境信号 0.05。
3. **内容信号门控**：只有 标题/演员/导演/编剧 命中才算相似；纯 分类+地区+年代 命中一律判 0。
4. **演员集合改余弦**：`inter / sqrt(|a|·|b|)` 替代 `inter / min(|a|,|b|)` —— 目标 10 位演员、候选只有 1 位客串时，旧版得 1.0，新版 0.32。
5. **标题相似度分母改 `max(len)`**：`0.6 × (LCS/max) + 0.4 × Jaccard`，短标题被长标题整体包含不再虚高。
6. **明星否定词**：标题含 访谈/花絮/盘点/预告/同款 等，明星命中从"强信号"降为"弱信号"（`RELATED_STAR_NEGATIVE_PATTERNS`）。

### 3.3 前后对比（同一组样本，用 `git show HEAD:app/related.py` 的旧代码实跑）

| 场景 | v1.9.3 | v1.10.0 | 说明 |
|---|---|---|---|
| 系列续作「流浪地球」vs「流浪地球2」（字段稀疏，同分类） | 0.829 | **0.691** | 仍是最高分，`reason=title,class` |
| 仅同分类+同地区+同年代（标题毫不相干） | 0.714 | **0.000（拒绝）** | 核心修复 |
| 「青云志」vs「青云路」（两字短标题前缀包含） | 0.286 | **0.000** | 短标题不再误配 |
| 同演员+同导演、片名不同 | 0.368 | **0.288** | 仍过阈值 0.15，排序正确 |
| 客串（4 位演员 vs 1 位） | 0.778 | **0.435** | 余弦抑制"客串当主演" |
| 完全无关（跨分类跨地区） | 0.143 | **0.000** | 低于阈值 |

**注意**：分数整体下调是设计结果（先验把地板压到 ~0.2）。若前端把 `score` 当"相似度 86%"展示，本版口径已变，**建议不再展示具体数值**。

## 4. 性能与容量（实测）

基准脚本 `scripts/bench_v110_perf.py`（1 万行合成数据、SQLite、`RELATED_STAR_INFER_MODE=off`）。

| 指标 | v1.9.3 | v1.10.0 | 变化 |
|---|---|---|---|
| `_load_feats`（1 万行） | 0.85 s / 29 MB | **0.96 s / 27 MB** | keyset 分页，内存恒定（旧版一次性 `fetchall`） |
| 整站重算（cap=600，旧默认） | 27.2 s = 2.72 ms/条 | 32.4 s = 3.24 ms/条 | 单条打分成本 +19%（先验 + reason 计算） |
| 整站重算（cap=140，新默认） | — | **8.3 s = 0.83 ms/条** | **较旧默认快 3.9×** |
| 单条增量重算 | 0.21 s | **0.20 s**（合并窗口内每站每窗口只付一次） | 持平，但触发次数大降 |

其他结构优化：

- **keyset 分页**（`vod_id > last_id`）替代 OFFSET：大表翻页不再"越翻越慢"。
- **全局重算闸门**（`RELATED_RECOMPUTE_CONCURRENCY=2`）：52 个源站同步完不再一起各起线程把内存拉到 GB 级。
- **增量重算窗口合并**（60 秒）：一轮增量同步的多次触发合并成一次全量加载；累计 ID 超过整站 30% 时直接转整站重算。
- **固定开销**：`list_tables` 一次取全（原每次 `information_schema` 往返）、`COUNT(*) FILTER` 把"视频数 + 缺演员数"合并成一次扫描、分类清单缓存 5 分钟、启动只校准"条数为 0"的源站。

容量参考：单源 20 万行 ≈ **0.6 GB** 内存峰值（2.92 KB/行），启动补齐是**串行**的，不会叠加；增量队列最多 2 个并发，NAS 上内存紧张可把 `RELATED_RECOMPUTE_CONCURRENCY` 降到 1。

## 5. 数据与功能级修复（部署方关心）

| 编号 | 问题（旧版实际后果） | 修复 | 升级后能看到什么 |
|---|---|---|---|
| **B1** | 批量加词条时只要有一条重复，PG 会把**整个事务**置为 aborted → 提交时 500，**整批一个字都没进去**（SQLite 测不出来） | 改 `ON CONFLICT DO NOTHING` 一次批量插入 | 粘贴含重复名字的名单不再失败，`added/skipped` 数字是真的 |
| **B2** | `reset_algo_version` 用 `engine.connect()` 做 DELETE 却不 commit —— 日志说"清空 N 条"，实际一行没删，**改算法版本完全不生效** | 改 `write_txn()`，并给读路径加 `algo_version` 过滤 | 本版 `algo_version` 1→2 会真正清空并重算 |
| **B3** | 词库删掉某明星后，旧 `vod_tag` 永久残留（UPSERT 的 `COALESCE(NULLIF())` 连源站重同步都洗不掉） | 缺演员行每次重建按当前词库重算，命中写入、不命中清空（`STAR_TAG_CLEAR_STALE`） | 面板删人后，该明星不再出现在别人的"明星作品"里 |
| **B4** | GBK 源站响应被 `errors="replace"` 解成 `����`，JSON 结构仍合法 → **整站片名被污染并覆盖进库** | 编码链 `utf-8-sig` → `Content-Type charset` → `gb18030` → `big5`；结果含 U+FFFD 即整页丢弃 | 日志出现"已按 gb18030 解码"；乱码片名不再入库（宁可漏一页并重试） |

其余已修：C1 夜间重建按"从未重建→最久未重建→小站优先"轮转、C2/C12 明星相关去掉 `count(distinct)`、C3 LIKE 通配符转义、C5 建表双检锁、C8 空 `vod_time` 条目不再永不入选、C9 `status` 变更也能落库、C11 `STAR_TAG_TOUCHED_CAP` 解耦、C14 删掉与主键重复的冗余唯一索引。

## 6. 部署与运维影响

### 6.1 会重算一次全站推荐（重要）

`RELATED_ALGO_VERSION` 默认从 `1` 改为 `2`，启动时：

1. `DELETE FROM vod_related WHERE algo_version <> '2'` —— **旧结果全清**；
2. 后台线程按源站**串行**全量重算；
3. 重算期间 `/api/v1/related` 走**实时兜底**（`fallback=true`，6 条，单条 SQL，仍然非空）。

按 1~2 ms/条（PG 多了写库往返）估算：单站 20 万行约 3~7 分钟，52 站串行约 **3~6 小时**。这期间推荐质量按兜底算，**功能不降级、不报错**。
→ 建议在低峰期升级；不想全量重算可先设 `RELATED_ALGO_VERSION=1` 启动（但等于放弃本次算法修复，不建议）。

### 6.2 搜索索引（pg_trgm）

启动后后台线程对每张 `vod_*` 表建 GIN 索引：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_trgm_vod_xxx ON vod_xxx USING gin (name gin_trgm_ops);
```

- `CONCURRENTLY` **不锁表**，建索引期间服务正常；
- 需要数据库账号有 `CREATE EXTENSION` 权限。docker-compose 默认的 `vodsync` 账号通常不是超级用户：**建扩展会失败**，此时只记一条 warning，搜索退化为顺序扫描（功能不变）。想启用就把扩展预先装好（`postgresql-contrib` + 用超级用户执行一次 `CREATE EXTENSION pg_trgm`）。
- 收益：`name LIKE '%关键词%'` 走索引（**3 字以上关键词明显**；2 字关键词因 trigram 无法提取仍走顺序扫描）。首建 52 个索引在百万行级库上约几分钟到十几分钟，只做一次。

### 6.3 启动与定时任务的变化

| 项 | 旧 | 新 |
|---|---|---|
| 启动条数校准 | 52 张表全量 `count(*)`（拖住调度器几十秒） | 只校准 `total_videos=0` 的源站；真值交给夜间校准 |
| 夜间校准 | 只重算推荐 | 重算推荐 **+ 精确重算全部 `total_videos`**（保证白天估值不会越飘越远） |
| 夜间明星重建 | 每晚捶同一批小站 | 按"从未重建 → 最久未重建 → 小站优先"轮转，同站最小间隔 20 小时 |


## 7. 新增 / 变更的环境变量

### 必须知道（默认值即可用，别删）

| 变量 | 默认 | 说明 |
|---|---|---|
| `RELATED_ALGO_VERSION` | **2**（原 1） | 改动即触发清空重算。回滚到 1.9.x 时手动设回 `1` |
| `TOTAL_APPROXIMATE_ENABLED` | true | 全站列表 `total` 用估值；设 false 恢复精确（52 次 count） |
| `CATEGORIES_CACHE_SECONDS` | 300 | 分类清单缓存；0 = 不缓存 |

## 8.5 v1.10.1 增量：详情字段透出（前端提的需求）

**问题**：线上 `/api/v1/videos/{slug}/{id}` 不返回 `vod_actor` / `vod_tag` —— 列 v1.9.0 起就在库里，
只是 `_detail_item` 没透出。于是 NAS 模式下演员只能拿 `star/related` 的 `stars` 兜底，
标签完全没有数据源、整行隐藏。

**改动**（纯新增，旧客户端零影响）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `vod_actor` | string | 演员，逗号分隔（源站原文，未归一化） |
| `vod_director` | string | 导演，逗号分隔 |
| `vod_area` | string | 地区，如 `中国大陆` |
| `vod_year` | string | 年代，4 位字符串，如 `2019` |
| `vod_tag` | string | 明星标签，逗号分隔（词库命中主名，服务端回填） |

- **恒为字符串**：库里缺失或为 NULL 都返回 `""`，客户端不用判 null、不用判 key 是否存在。
- **生效范围**：`/videos/{slug}/{id}`、`?ids=` 批量详情、`?ac=detail` 列表 **三条路径都有**
  （`ac=detail` 与 `content`/`play_url` 同一条 SQL 取回，不增加往返；深翻页 UNION 路径也带）；
  普通列表模式（不带 `ac`/`ids`）**不带**，避免每页多传 5 个字段。
- **取值容错**：`_detail_item` 有 3 个调用点，其中多源归并列表的行是 multiquery 组装的 dict，
  没有这些列 —— 硬取会 KeyError 打挂整个列表接口。现在统一走 `_pick`（缺列/NULL → `""`）。
- `vod_tag` 与 `star/related` 的 `stars` 同源但不同性质：`vod_tag` 是**落库静态值**（每晚轮转重建），
  `stars` 是**实时计算**。不一致时以 `stars` 为准。

前端可以这样用（推荐顺序）：

```js
const d = resp.detail;
const actors = splitComma(d.vod_actor);      // 有值就用它，不必再请求 star/related
const tags   = splitComma(d.vod_tag);        // 标签终于有数据源了
if (!actors.length) { /* 再回落到 star/related 的 stars */ }
```
