# v1.10.x → v1.11.0 升级报告（播放线路识别 / 过滤 / 排序）

> 面向：客户端开发（第 1~4 节）+ 运维/部署（第 5~7 节）。
> 结论先行：**接口全部向后兼容，`vod_play_url` 逐字节不变**。客户端不改代码也能跑，
> 但改一行（优先用 `vod_play_list` 而不是自己 `split`）就能修掉「第一条线路播不出来」。
> 对应需求文档：`vodsync-播放线路过滤-需求.md`（验收标准见第 9 节）。

---

## 1. 前端对接清单（先看这张表）

| # | 变化 | 影响 | 前端要做什么 |
|---|---|---|---|
| 1 | `vod_play_list[]` 新增 `from` / `type` / `playable` / `original_index` | 纯新增字段 | **推荐**：改用它渲染线路；`playable=false` 的线路置灰或直接不显示 |
| 2 | `vod_play_list` 可能**变少**（默认 `filter` 会剔除分享页线路） | **行为变化** | 不要假设「线路数 == 上游线路数」；不要再按数组下标缓存「第 N 条线路」 |
| 3 | `name` 编号改为**过滤后**序号，并可追加 provider：「线路1 (ffm3u8)」 | 字符串内容变化 | 如果做了 name 文案替换/匹配，改成显示 `name` 原文 |
| 4 | 详情条目新增 `play_from`（上游 provider 串，如 `feifan$$$ffm3u8`） | 纯新增字段 | 通常不用；排障时有用 |
| 5 | 响应顶层新增 `play_line_filtered: true`（**仅在真的过滤掉线路时出现**） | 纯新增字段 | 可用于埋点/灰度对比；不存在 ≠ 出错 |
| 6 | 三个接口都支持 `?play_raw=1` | 纯新增参数 | 排障用：拿到未过滤、未排序的原始线路列表 |
| 7 | 面板/API 可按源站覆盖策略 | 纯新增 | 后台需要就在源站列表加下拉（`POST .../play-line-policy`） |
| 8 | `/api/v1/stats` 新增 `play_line` 段 | 纯新增字段 | 运维观测用 |

> 只做第 1 项 + 第 2 项，就已经能解决「第一条线路是 H5 分享页播不出来」这个线上问题。

## 2. 为什么必须改（问题复盘）

非凡资源站（`feifan`）**100% 的记录**长这样：

```
vod_play_from = "feifan$$$ffm3u8"
vod_play_url  = "第01集$https://x.com/share/ab12cd#第02集$...#...$$$第01集$https://x.com/20240101/index.m3u8#..."
                 └────────── 第 1 条：H5 分享页 ──────────┘     └────── 第 2 条：真直链 ──────┘
```

- `/share/<hash>` 返回 `200 text/html`，页面里没有可播地址，真实 m3u8 由 JS 拼出来、**带会过期的 `?sign=`**。
- 旧实现把上游 `vod_play_from` 丢弃、`parse_play_url()` 只按序号命名线路、不做任何形态判断。
- 客户端按顺序选第 1 条 → 必然播放失败。**用户看到的是「这部片子坏了」，不是「线路选错了」。**

修法不是去解析分享页（会引入签名过期、二次请求、反爬等一堆问题），而是**在读接口上认出并剔除这类线路**。

## 3. 接口详解

### 3.1 详情条目新增字段

`GET /api/v1/videos/{vod_id}`、`GET /api/v1/videos?ids=...`、MacCMS 兼容
`/api.php/provide/vod/?ac=detail` 三条路径**都**返回同一结构：

```json
{
  "code": 1,
  "video": {
    "source": "feifan",
    "vod_id": 123456,
    "vod_name": "示例影片",
    "vod_play_from": "vodsync",
    "play_from": "feifan$$$ffm3u8",
    "vod_play_url": "第01集$https://x.com/share/ab12cd#...$$$第01集$https://x.com/20240101/index.m3u8#...",
    "vod_play_list": [
      {
        "name": "线路1 (ffm3u8)",
        "from": "ffm3u8",
        "type": "m3u8",
        "playable": true,
        "original_index": 1,
        "episodes": [
          { "name": "第01集", "url": "https://x.com/20240101/index.m3u8" }
        ]
      }
    ]
  },
  "play_line_filtered": true
}
```

字段语义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `play_from` | string | 上游 `vod_play_from` 原始串，与 `vod_play_url` 的线路顺序**一一对应**。存量行为空串（未回填，见第 6 节） |
| `vod_play_list[].from` | string | 该条线路的 provider。`play_from` 缺失时为空串 |
| `vod_play_list[].type` | string | `m3u8` / `mp4` / `flv` / `mkv` / `page` / `unknown` |
| `vod_play_list[].playable` | bool | `type != "page"`。**`false` 表示这条线路是网页，播放器直接请求必然失败** |
| `vod_play_list[].original_index` | int | 在上游原始串里的下标（**0 基**）。跨策略/跨版本稳定，用它做「用户上次选的是哪条线路」的缓存键 |
| `vod_play_list[].name` | string | 编号是**过滤后**的序号；`PLAY_LINE_NAME_WITH_FROM=true`（默认）时追加 provider |
| `vod_play_list[].episodes` | array | 未变 |

`vod_play_from` **仍然是常量 `"vodsync"`**，没有改成上游 provider 串 —— 老客户端有依赖它的，语义变更属于破坏性改动。真实 provider 看 `play_from` 和每条线路的 `from`。

### 3.2 `?play_raw=1`（排障开关）

三个接口都支持：

```
GET /api/v1/videos/{vod_id}?play_raw=1
GET /api/v1/videos?ids=1,2,3&play_raw=1
GET /api.php/provide/vod/?ac=detail&ids=123456&play_raw=1
```

效果：**不过滤、不排序、名字不带 provider**，等价于 v1.10.x 的行为。
此时 `play_line_filtered` 永远不会出现。用来回答「到底是上游就没这条线路，还是被我过滤了」。

### 3.3 `play_line_filtered` 语义（别用错）

- 只在**本次响应里真的有线路被剔除**时出现，值为 `true`；没有这个字段 ≠ 出错。
- 它是**响应级**的：批量详情里任意一条影片被过滤过，顶层就是 `true`。要精确到单条，看该条的 `vod_play_list[].playable` / `original_index` 有没有跳号。
- 命中安全阀（过滤后 0 条 → 整条回退原始列表）时**不会**出现 `play_line_filtered`，但 `/stats` 的 `play_line.fallback_total` 会 +1。

### 3.4 源站级策略

```
POST /api/v1/sources/feifan/play-line-policy?policy=filter
```

| policy | 含义 |
|---|---|
| `inherit` | **默认**。跟随全局 `PLAY_LINE_POLICY` |
| `off` | 该站不过滤（源站自己的线路本来就干净时用） |
| `filter` | 剔除 `page` 类型线路（推荐给非凡这类站） |
| `whitelist` | 只保留 `PLAY_LINE_KEEP_EXT` 里的媒体扩展名（更严格：`unknown` 也会被剔） |

非法值 → `400`。写库后**立即生效**（面板改完不用重启，内部会失效策略缓存）。

`GET /api/v1/sources` 每行新增三个字段：

```json
{
  "play_line_policy": "filter",        // 磁盘值（inherit 表示跟随全局）
  "play_line_effective": "filter",     // 最终生效值（已解析 inherit）
  "play_line": { "lines": 1284, "dropped": 642, "fallback": 0 }
}
```

`play_line` 是**本次进程启动以来**的读侧累计（重启清零），面板据此显示「线路 2→1（过滤 1 条 page）」。

### 3.5 `/api/v1/stats` 新增段

```json
"play_line": {
  "policy": "filter",
  "filtered_total": 642,       // 累计剔除的线路数
  "fallback_total": 3,         // 命中安全阀的次数（应接近 0）
  "page_lines_total": 642,     // 累计识别出的 page 线路数
  "lines_total": 1926,         // 累计解析的线路总数
  "uptime_seconds": 86400
}
```

## 4. 判定规则（什么线路会被剔）

`classify_play_line(url)` 是**纯字符串函数**：只看 URL 的 **path**（去掉 `scheme://host`、去掉 `?query`、去掉 `#fragment`，转小写），不发网络请求。

判定顺序（**扩展名优先**）：

1. path 以 `.m3u8` / `.mp4` / `.flv` / `.mkv` 结尾 → 对应媒体类型（`m3u8` 等）
2. path 命中 `PLAY_LINE_DROP_PATTERNS`（默认 `/share/,/play/,.html,.htm`，子串、大小写不敏感；`re:` 前缀按正则）→ `page`
3. 其余 → `unknown`

**为什么扩展名优先（与需求原文顺序不同）**：需求写的是「先黑名单再扩展名」，但
`https://x/play/<id>/index.m3u8` 这种「`/play/` 前缀 + 真 m3u8」非常常见，
按原文顺序会把它误判成 page 直接杀掉。以 `.m3u8` 结尾必然是媒体播放列表，这个证据强于路径前缀。
反过来的情况（页面地址以 `.m3u8` 结尾却返回 HTML）实际不存在。
测试 `A5` 专门覆盖这一点。

策略矩阵：

| type | `filter` | `whitelist` | `off` |
|---|---|---|---|
| `m3u8` / `mp4` / `flv` / `mkv` | 保留 | 保留 | 保留 |
| `page` | **剔除** | **剔除** | 保留 |
| `unknown` | 保留 | **剔除**（不在 KEEP_EXT 里） | 保留 |

排序（`PLAY_LINE_PREFER_DIRECT=true`，默认开）：
`m3u8 > mp4 > flv > mkv > unknown > page`，**同类型内保持上游原顺序**（稳定排序）。
所以过滤 + 排序之后，`original_index` 可能出现 `1, 0` 这种「不递增」——这是正常的，它记录的是上游位置。

**安全阀（必读）**：如果过滤后线路数 < `PLAY_LINE_MIN_KEEP`（默认 1），**整条影片回退未过滤的原始列表**，并打一条 WARNING：

```
播放线路过滤后仅剩 0 条（策略 filter，原始 2 条），已回退未过滤结果: https://x.com/share/...
```

设计意图：宁可让用户看到一条播不出来的线路（可以换线/反馈），也不能让整部片子变成「无线路」。

## 5. 数据库变更

| 变更 | 说明 |
|---|---|
| `vod_<slug>.play_from TEXT NULL` | 上游 `vod_play_from`。每个源站一张表，都要补 |
| `sources.play_line_policy VARCHAR(16) DEFAULT 'inherit'` | 源站级策略 |

两者都走 **v1.9.0 起的「启动自动补列」** 机制：服务启动时 `_migrate()` 检查 `information_schema`，缺列就 `ALTER TABLE ... ADD COLUMN`。**不阻塞启动、不需要手工 SQL、不需要重新同步。**

存量 657 万行的 `play_from` 是 `NULL` —— 这**不影响功能**：`classify_play_line()` 只用 URL 形态就够判断，provider 只是让线路名更好看。想补上就做第 6 节的回填，不做也完全可用。

## 6. 可选：回填 `play_from`

```bash
curl -X POST "http://127.0.0.1:8181/api/v1/sync/feifan?mode=backfill_play_from"
```

行为：

- 只翻 `ac=detail` 列表页，只取 `(vod_id, vod_play_from)` 两列 —— **不重新入库、不改 `vod_play_url`、不动水位线/断点**。
- 逐页 `UPDATE ... WHERE vod_id = ?`，每 20 页打一次进度日志。
- **幂等**，随时可重跑、可中途停（有断点检查）。
- 上游返回空值/没有 `vod_play_from` 时**跳过**该行，不会把已有值擦成空。
- 完成后 `stats` 里能看到本次 `fetched / inserted / updated / pages`（回填模式下 `inserted` 恒为 0）。

657 万行全量回填的耗时取决于源站 API 速度，按单站典型 10 万条估算在几分钟量级。**非必需步骤**，建议只对「你想让线路名显示 provider」的站跑。

## 8. 新增环境变量

默认值即可用，不用动。

| 变量 | 默认 | 说明 |
|---|---|---|
| `PLAY_LINE_POLICY` | `filter` | 全局策略：`off` / `filter` / `whitelist` |
| `PLAY_LINE_DROP_PATTERNS` | `/share/,/play/,.html,.htm` | `filter` 模式下判为页面的 path 特征（子串；`re:` 前缀按正则） |
| `PLAY_LINE_KEEP_EXT` | `m3u8,mp4,flv,mkv` | `whitelist` 模式保留的扩展名 |
| `PLAY_LINE_PREFER_DIRECT` | `true` | 直链优先排序（同类型保持上游顺序） |
| `PLAY_LINE_NAME_WITH_FROM` | `true` | 线路名追加 provider：「线路2 (ffm3u8)」 |
| `PLAY_LINE_MIN_KEEP` | `1` | 安全阀阈值：过滤后低于此值则整条回退 |
| `PLAY_LINE_PROBE_HTML` | `false` | 对 `unknown` 地址做 HEAD 探测（**读路径发网络请求，会拖慢详情**，默认关） |
| `PLAY_LINE_PROBE_TIMEOUT` | `1.5` | 探测超时（秒） |
| `PLAY_LINE_POLICY_CACHE_SECONDS` | `30` | 源站策略缓存；面板改下拉会立即失效，这个只兜底多进程/直接改库 |

`PLAY_LINE_DROP_PATTERNS` 的两个坑：

- **只看 path**：`https://x.com/vodplay/1-1-1.html?from=share` 里 query 的 `share` 不影响判定。
- 子串匹配很宽松：写 `/share/` 是安全的（带前后斜杠），**不要**写成 `share`，否则 `.../shareholder.mp4` 会被误伤。不过 `.mp4` 结尾的地址有扩展名优先保护，实际仍会保留 —— 但别依赖这个兜底。

## 10. 一页速查（copy-paste 版）

```kotlin
// 线路数据类（v1.11.0）
data class PlayLine(
    val name: String,           // "线路1 (ffm3u8)" —— 直接显示
    val from: String = "",      // provider
    val type: String = "",      // m3u8 / mp4 / flv / mkv / page / unknown
    val playable: Boolean = true,
    val originalIndex: Int = -1,
    val episodes: List<Episode> = emptyList(),
)

// 渲染：过滤掉不可播的，其余按服务端给的顺序（已经是直链优先）
val playable = video.vodPlayList.filter { it.playable }

// 播放：取第一条
val line = playable.firstOrNull() ?: return showError("该影片暂无可用线路")
val url = line.episodes.firstOrNull()?.url ?: return showError("该线路无剧集")

// 记住用户选的线路 —— 用 originalIndex，不要用数组下标（线路数会变）
prefs.edit().putInt("line_${video.vodId}", line.originalIndex).apply()
```

排障三步：

1. `?play_raw=1` 还播不出来 → 上游线路本身就是坏的，不是过滤的问题。
2. `?play_raw=1` 能播、默认不能播 → 检查 `PLAY_LINE_DROP_PATTERNS` 是不是把真直链误杀了（把它临时设成空串复测）。
3. 默认响应里线路数比上游少很多 → `curl /api/v1/sources` 看该站 `play_line_effective`，
   必要时 `POST /api/v1/sources/<slug>/play-line-policy?policy=off` 单站关掉。
